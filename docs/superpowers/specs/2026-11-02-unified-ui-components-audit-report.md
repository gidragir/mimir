## Архитектурный вердикт (Executive Summary)

Главная архитектурная ошибка спецификации — **попытка искусственно навязать единую TSX/Preact UI-библиотеку гетерогенным клиентам (`browser-extension`, `obsidian-plugin`, `web-ui`), игнорируя существующий рантайм Kotlin/JS, границы владения данными и текущую инфраструктуру сборки монорепозитория.**

1. **Отрицательный ROI миграции `browser-extension`:** Расширение уже полностью реализовано на Kotlin/JS. Его UI-слой (`PopupDomView.kt`) занимает всего **186 строк** тривиального DOM-кода, полностью протестирован (Karma + Headless Chrome) и весит ~5 КБ CSS. Замена 186 строк чистого кода на стек Preact + TSX + Tailwind v4 порождает громоздкий гибридный франкенштейн-рантайм (Kotlin/JS Ktor + Coroutines + Preact VDOM) с колоссальными накладными расходами на мосты данных и маршалинг.
2. **Слепая зона интеропа Kotlin/JS и Preact:** В спеке полностью отсутствует техническое описание того, как Kotlin `StateFlow<ExtensionUiState>` (с sealed-иерархиями, коллекциями и coroutine-скоупами) передается в Preact без потерь типизации, накладных расходов на глубокое клонирование и проблем с `@JsExport`.
3. **Конфликт систем сборки (Gradle vs pnpm vs Yarn) и CI:** Kotlin/JS исторически использует Yarn v1 для управления npm-зависимостями (см. комментарий в `.github/workflows/ci.yml`: `поле packageManager ломает yarn, которым Kotlin/JS ставит npm-зависимости`). В `ci.yml` шаг `./gradlew build` вызывается ДО `pnpm install`. Добавление TS-пакета ломает текущий CI-пайплайн и контракт Changesets (`.changeset/config.json`, `scripts/sync-version.mjs`).
4. **Архитектурный Overengineering в UI-слое:** Внедрение `StorageAuthStrategy`, `CredentialsFormStrategy` и `StorageProviderDescriptor` (WebDAV, Nextcloud, S3) в презентационную UI-библиотеку грубо нарушает принцип Ports & Adapters и правило YAGNI. Mimir поддерживает только Google Drive; логика авторизации и возможности провайдеров принадлежат доменному ядру (`core`/`drive`), а не dumb-компонентам интерфейса.

## 1. Анализ ROI и практической целесообразности

### 1.1 Отказ от Compose Wasm — верное решение, но ложный вывод
- **Отказ от Compose Wasm для веба оправдан на 100%:** Бандл 15–25 МБ, Canvas/WebGL-рендеринг, отсутствие доступности (a11y), размытие шрифтов и принципиальная несовместимость с жестким CSP Chrome MV3 (`script-src 'self'`, запрет динамической компиляции wasm в ряде контекстов, задержка cold start в popup) делают Compose Wasm непригодным для веб-клиентов.
- **Ошибочный вывод:** Из негодности Compose Wasm не следует необходимость создания общего пакета компонентов `@mimir/ui-web` для всех платформ. Реальный потребитель полноценного веб-интерфейса прямо сейчас ровно один — `web-ui` (SPA для демона Mimir).

### 1.2 Миграция `browser-extension`: почему это вредно
- **Текущее состояние:**
  - `browser-extension/src/jsMain/kotlin/dev/mimir/extension/ui/PopupDomView.kt` — всего **186 строк**.
  - `AuthScreens.kt` — 87 строк.
  - `popup.css` — 85 строк (5.4 КБ сырого текста, ~1.8 КБ gzip).
  - Архитектура расширения монолитна и гармонична: криптография (`RcloneCipher`), Ktor HTTP-клиент, OAuth PKCE перехват, хранилище токенов и DOM-представление скомпилированы единым Kotlin/JS Webpack-бандлом (`popup.js`).
- **Что предлагает спека:**
  - Оставить контроллер на Kotlin/JS, но рендеринг вынести в Preact TSX.
  - Это создает худший из возможных архитектурных паттернов: **двухъязычный UI-интероп**. Ради устранения 186 строк надежного, детерминированного DOM-кода в проект затягивается рантайм Preact, сборка TSX, генерация `.d.ts` и слой адаптеров состояния.
  - Если расширению требуется редизайн по токенам Obsidian — достаточно переписать `popup.css`, переведя его на CSS-переменные дизайн-системы, не трогая стабильный Kotlin-код.

### 1.3 `obsidian-plugin`: непонимание целевой платформы
- Спека указывает `obsidian-plugin` как потенциального потребителя компонентов `@mimir/ui-web`.
- В Obsidian плагины живут внутри чужого DOM и обязаны подчиняться дизайн-системе Obsidian API (`Setting`, `Notice`, `Modal`, `ItemView`, переменные `--background-primary`, `--text-normal` и т.д.).
- Подключение Tailwind CSS v4 или собственных компонентов со своей структурой классов в Obsidian приводит либо к конфликтам стилей (стилевой дрейф тем Obsidian), либо к раздуванию бандла плагина. На данный момент `obsidian-plugin` содержит всего 15 строк кода (`StubSyncEngine`). Затачивать общую библиотеку под него — классический пример Premature Optimization.

### 1.4 Резюме по ROI
| Направление | Предложение спеки | Реальный эффект | Оценка ROI |
| :--- | :--- | :--- | :--- |
| **`web-ui`** | Preact SPA на базе `@mimir/ui-web` | Замена мертворожденного Compose Wasm на легкий Preact SPA | **Высокий (+)** |
| **`browser-extension`** | Миграция с Kotlin DOM на Preact TSX | Усложнение архитектуры, риски регрессий, дублирование рантаймов | **Отрицательный (-)** |
| **`obsidian-plugin`** | Использование компонентов `@mimir/ui-web` | Конфликт с темами Obsidian, раздувание бандла | **Отрицательный (-)** |
| **Выделение `@mimir/ui-web`** | Отдельный пакет в pnpm workspace | Оверинжиниринг для единственного реального потребителя (`web-ui`) | **Низкий (0)** |

## 2. Анализ соответствия Best Practices современного фронтенда (2026)

### 2.1 Стек технологий
1. **Preact 10+:**
   - Выбор Preact оправдан (минимальный вес ~4 КБ gzip).
   - **Упущение:** Спека говорит об UDF, но ничего не говорит о механизме реактивности. В экосистеме Preact стандартом де-факто являются **Preact Signals** (`@preact/signals`). Передача состояния «сверху вниз» через чистый props-drilling на формах авторизации и дереве файлов вызовет избыточные ререндеры или заставит писать бойлерплейт с контекстами.
2. **Tailwind CSS v4:**
   - Выбор Tailwind v4 с конфигурацией `@theme` в CSS прогрессивен.
   - **Критический риск — Preflight Leakage:** Tailwind по умолчанию включает глобальный сброс стилей (Preflight). Если скомпилированный `mimir-ui.css` будет подключен в `browser-extension` или гипотетический `obsidian-plugin`, Preflight сломает стили родительских страниц/хоста. Спека обязана потребовать либо отключение preflight, либо жесткую изоляцию через CSS Cascade Layers (`@layer`) или префиксацию.
3. **Инструмент сборки (tsup vs Vite):**
   - Формулировка «`tsup` или `vite library mode`» недопустима для финальной спецификации. 
   - `tsup` (esbuild) идеален для чистых библиотек типов и JS без сложных CSS-ассетов. Для библиотеки с Tailwind v4 и статическими стилями стандарт 2026 года — **Vite 6+ в режиме библиотеки** с плагином `@tailwindcss/vite` или специализированный tsup-пайплайн с явной компиляцией стилей. Должен быть зафиксирован один конкретный инструмент.
4. **Контроль бандла и Chrome MV3 CSP:**
   - Требование `< 20 КБ gzip` для JS-библиотеки реалистично.
   - Требование по CSP (`script-src 'self'`) соблюдается при условии отсутствия динамического `eval`/`new Function` (Preact и Tailwind v4 чисты от этого).
   - **Слепая зона — Иконки:** В разделе 6.1 упомянут атом `Icon`. Спека не определяет источник иконок. Если разработчик подключит `lucide-preact` без точечного tree-shaking, бандл мгновенно вырастет на 40–60 КБ. Требуется явный запрет тяжелых иконочных пакетов и фиксация inline SVG / спрайтов.

### 2.2 Чистота архитектурных паттернов (Anti-Patterns Warning)
1. **Искажение Ports & Adapters:**
   - Спека заявляет: *«Пакет @mimir/ui-web выступает портом отображения»*.
   - Но тут же определяет внутри UI-пакета: `StorageAuthStrategy`, `OAuthRedirectStrategy`, `DeviceCodeStrategy`, `CredentialsFormStrategy`.
   - **Ошибка:** Это грубое нарушение разделения ответственности. Способ авторизации хранилища — это бизнес-логика инфраструктурного уровня (`drive` / `core`), а не UI-компонента.
   - UI-библиотека должна быть строго «глупой» (Presentational). Она не должна знать концепций «OAuth Redirect» или «Device Code». Она должна оперировать понятиями: `ActionCard`, `PinCodeDisplay`, `DynamicForm(fields)`. Описание полей формы и шагов авторизации должно приходить в UI в виде DTO/схемы данных, а не зашиваться в стратегии внутри React/Preact-компонентов.

## 3. Критические риски, слепые зоны и архитектурные ловушки

### 3.1 Архитектурная пропасть: Интероп Kotlin/JS <-> Preact TSX
Это самый опасный дефект спецификации. Спека декларирует:
> *«Контроллер ExtensionController.kt передает состояние через подписку (stateFlow/listener), а Preact-приложение рендерит SplitWorkspaceLayout»*.

Что это означает на практике:
1. **Несовместимость типов:** `ExtensionUiState` в Kotlin — это `sealed interface` с вложенными `data class` (`AuthRequired`, `UnlockRequired`, `VaultReady`).
   - Kotlin/JS не компилирует sealed-интерфейсы в чистые TypeScript-дискриминированные объединения (discriminated unions). Поля классов получают служебные префиксы, геттеры генерируются как функции, а коллекции (`List`, `Set`) — это не JS `Array` и `Set`, а Kotlin-обертки `KtList`.
   - Использование аннотации `@JsExport` на сложных структурах в KMP имеет жесткие ограничения (не поддерживаются интерфейсы вне определенных рамок, generic-типы, suspend-функции).
2. **Подписка на StateFlow:** В JS нет корутин Kotlin. Чтобы Preact подписался на `StateFlow`, в Kotlin/JS потребуется создать рукописный мост-адаптер (`StateFlowBridge`), запускающий корутину в `MainScope` и вызывающий коллбэк JS при каждом эмите.
3. **Граница сборки (Who builds whom?):**
   - Если Kotlin/JS компилируется в `popup.js`, как он подтягивает Preact-компоненты? Через `npm(...)` зависимость в Gradle? Тогда Kotlin/JS должен вызывать Preact через сырой `js("...")` или рукописные externals.
   - Если сборку финализирует Vite/Rollup (собирая `popup.tsx`), то Kotlin/JS должен собираться как npm-библиотека (`binaries.library()`), публиковать свои `.d.ts` и отдавать контроллер наружу. Но `browser-extension/build.gradle.kts` настроен на исполняемый таргет `binaries.executable()` с Webpack!
   - **Итог:** Спецификация предлагает революцию в UI, не ответив на вопрос, как собрать проект.

### 3.2 Конфликт сборочной инфраструктуры (Gradle + pnpm workspace + Yarn)
1. **Yarn-ловушка Kotlin/JS:**
   В файле `.github/workflows/ci.yml` зафиксирован жесткий инвариант:
   `version: 10.18.0 # не в package.json: поле packageManager ломает yarn, которым Kotlin/JS ставит npm-зависимости`.
   Gradle Kotlin Multiplatform плагин под капотом использует свой собственный Yarn (`kotlin-js-store/yarn.lock`). Внедрение pnpm-пакета `@mimir/ui-web` в общий корень создает риск интерференции пакетных менеджеров.
2. **Порядок сборки в CI:**
   Текущий шаг CI:
   ```bash
   - run: mise run build # -> ./gradlew build
   ```
   Gradle ничего не знает о `pnpm run build` в `packages/ui-web`. Если задача расширения или веб-интерфейса в Gradle начнет требовать артефакты из `packages/ui-web/dist`, сборка в CI упадет, потому что `pnpm install` и сборка TS-библиотеки не выполнялись.
3. **Синхронизация версий (Changesets):**
   Скрипт `scripts/sync-version.mjs` проверяет:
   ```javascript
   const workspaces = [...readFileSync('pnpm-workspace.yaml', 'utf8').matchAll(/^\s+-\s+(\S+)\s*$/gm)].map((m) => m[1]);
   ```
   и сверяет версии во ВСЕХ `package.json` с `gradle.properties`. В `.changeset/config.json` зафиксирован список пакетов группы `fixed`.
   Спецификация ни словом не упоминает добавление `@mimir/ui-web` в `pnpm-workspace.yaml`, `.changeset/config.json` и синхронизацию версий, что гарантированно сломает релизный пайплайн.

### 3.3 Иллюзия Single Source of Truth для токенов
В разделе 4.2 написано:
> *«Токены поддерживаются декларативно в CSS Variables и зеркалируются в Kotlin MimirTheme/ObsidianStyle без усложнения инфраструктуры тяжелыми генераторами (Style Dictionary).»*

- «Ручное зеркалирование» — это прямой антипод Single Source of Truth. Это **два независимых источника истины**.
- При изменении токена в CSS неизбежно возникнет рассинхронизация с нативным Compose (`MimirTheme.kt`). Любое ручное дублирование в проекте с жесткими инвариантами приводит к визуальному дрейфу.

### 3.4 Дублирование Markdown-парсера
- В `browser-extension` уже есть `SafeMarkdownRenderer.kt`, оттестированный регулярными выражениями и защищенный от XSS/CSP инъекций.
- Спека требует написать его TSX-клон `SafeMarkdownViewer`.
- Поддержка двух regex-парсеров одного диалекта Markdown (с поддержкой `[[wikilinks]]`, задач и блоков кода) на двух разных языках приведет к расхождению в парсинге и логике санитизации.

## 4. Конкретные рекомендации по переработке спецификации

Чтобы спецификация стала жизнеспособной, надежной и соответствующей духу Mimir, ее необходимо переработать по следующим пунктам:

### 4.1 Изменение скоупа и прагматичный ROI (Scope Revision)
1. **Исключить миграцию `browser-extension` на Preact:**
   - Оставить `PopupDomView.kt` и Kotlin/JS в расширении. 186 строк стабильного кода не требуют рефакторинга ради рефакторинга.
   - Унификацию стиля расширения решить **исключительно на уровне CSS-токенов**: сгенерировать единый `tokens.css` и подключить его в `popup.html`.
2. **Исключить `obsidian-plugin` из потребителей Preact UI:**
   - Зафиксировать в не-целях: плагин Obsidian использует нативный DOM API Obsidian и системные стили темы хоста.
3. **Сфокусировать спеку строго на `web-ui` (SPA):**
   - Назначение проекта — разработка современного, легковесного Preact SPA для `web-ui`, раздаваемого Ktor-демоном (`daemon`).
   - До момента появления второго РЕАЛЬНОГО веб-клиента не усложнять монорепозиторий отдельным пакетом `packages/ui-web`. Реализовать компоненты непосредственно внутри модуля `web-ui/` (с возможностью легкого выделения в будущем).

### 4.2 Архитектурная чистота (Dumb Components & No Overengineering)
1. **Удалить бизнес-логику провайдеров из UI:**
   - Вырезать классы `StorageAuthStrategy`, `OAuthRedirectStrategy`, `DeviceCodeStrategy`.
   - Заменить их на чисто декларативные компоненты:
     - `OAuthLoginCard(providerTitle, onStartLogin)`
     - `DeviceCodeCard(userCode, verificationUrl, onCopy)`
     - `AccountStatusCard(email, storageUsed, onLogout)`
   - Все решения о том, какой экран показывать, принимает презентер/контроллер приложения на основе состояния демона/рантайма.
2. **Очистить спеку от WebDAV, S3, Nextcloud:**
   - Следовать правилу YAGNI. В Mimir реализован только Google Drive. Проектировать формы учетных данных под несуществующие бэкенды запрещено.

### 4.3 Настоящий Single Source of Truth для токенов
- Создать единый декларативный JSON-файл токенов: `design/tokens.json`.
- Написать минимальный скрипт на Node.js (без тяжелых библиотек): `scripts/generate-tokens.mjs` (~35 строк), который генерирует:
  1. `web-ui/src/styles/tokens.css` (CSS Custom Properties).
  2. `ui/src/commonMain/kotlin/dev/mimir/ui/MimirTokens.kt` (Compose Color & Dp константы).
- Добавить запуск генератора в `pnpm run build` и проверку отсутствия дрейфа в CI.

### 4.4 Изоляция стилей Tailwind v4
- В конфигурации Tailwind для веб-интерфейса явно зафиксировать изоляцию базовых стилей:
  ```css
  @layer theme, base, components, utilities;
  @import "tailwindcss";
  ```
- Исключить глобальные селекторы, влияющие на теги верхнего уровня вне контейнера приложения `#app`.

### 4.5 Интеграция с Gradle, pnpm и Changesets
Если компонентная библиотека все же выделяется в отдельный пакет:
1. Зафиксировать обязательные изменения в `pnpm-workspace.yaml` и `.changeset/config.json` (добавление пакета в группу `fixed`).
2. В `web-ui/build.gradle.kts` добавить явную связку задач: сборка дистрибутива `web-ui` запускает команду `pnpm --filter @mimir/web-ui build` через `Exec`-таску, а скомпилированный `dist/` копируется в ресурсы для раздачи Ktor-сервером демона.
3. Обновить `ci.yml`, чтобы вызов `pnpm install` и сборка веб-пакетов происходили ДО запуска тестов и сборки Gradle-модулей, зависящих от веб-ассетов.

### Итоговый вердикт
Спецификация в текущем виде пытается решить несуществующую проблему переиспользования UI ценой колоссального усложнения архитектуры расширения и сборочной инфраструктуры. Документ требует отзыва на доработку: перефокусировать на легковесный Preact SPA внутри `web-ui`, сохранить целостность `browser-extension` на Kotlin/JS и автоматизировать единый источник токенов.
