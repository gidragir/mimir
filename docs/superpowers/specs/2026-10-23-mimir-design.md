# Mimir — синхронизатор Obsidian vault через Google Drive с шифрованием

Дата: 2026-10-23
Статус: черновик на согласование
Рабочее название: **Mimir** (по имени каталога проекта; финальное имя не обсуждалось)

Этот документ описывает **скелет проекта**, с которого начнётся разработка, и замысел продукта, под который скелет закладывается. Реальная синхронизация и шифрование в объём скелета не входят.

---

## 1. Замысел и зачем

Пользователь ведёт Obsidian vault на Linux (Arch), Windows и Android. Сейчас на каждой платформе свой способ синхронизации, и ни один не устраивает полностью:

- **Android**: «непонятные» конфликты синхронизации, хотя в `.obsidian` ничего значимого не менялось.
- **Linux**: rclone настраивается через CLI, много непонятных настроек, двунаправленная синхронизация работает с проблемами.
- **Windows**: Google Drive Desktop работает хорошо (диск подключён, Obsidian смотрит в папку), но для установки нужны права администратора, которых у разработчиков часто нет.

Отдельная причина для шифрования: Gemini читает папку Google Drive с заметками и подмешивает личный контекст туда, где он не нужен. Заметки в Drive должны быть нечитаемы для Gemini и любых сервисов с доступом к Drive.

Mimir — **один открытый инструмент на всех платформах**, который ощущается как Google Drive Desktop: один раз указал папку vault и пароль, дальше всё синхронизируется само. Локально лежат обычные `.md`, в Drive только зашифрованные данные.

Проект будет open source (в отличие от многих аналогов), но на старте живёт в **приватном репозитории GitHub**, лицензия пока не выбрана.

## 2. Цели

1. Двусторонняя фоновая синхронизация локальной папки vault с Google Drive на Windows, Linux (в первую очередь Arch) и Android.
2. Сквозное шифрование: в Drive хранятся зашифрованные содержимое **и имена** файлов/папок. Локально vault остаётся обычной папкой, Obsidian про Mimir ничего не знает.
3. Один пароль на все устройства. Вводится один раз на устройстве и сохраняется локально.
4. **Профилактика конфликтов важнее красивого их разрешения.** Устройство очевидно (не только уведомлением) показывает, что у него есть неотправленные изменения или что оно давно не получало свежих.
5. Если конфликт случился, простой экран без git-терминологии: две версии рядом, «оставить эту», «оставить ту», «объединить».
6. Правила синхронизации, особенно для телефона: только по Wi-Fi, по расписанию (окна времени), при появлении Wi-Fi.
7. Быстрый просмотр зашифрованной заметки из Drive без Obsidian и без полной синхронизации: в приложении, в браузерном расширении (поверх Drive) и в web UI.
8. Установка без прав администратора и без отдельной установки зависимостей (Java и т. п.).
9. Сборка всех артефактов в GitHub Actions.

## 3. Не цели

- Совместная работа нескольких людей над одним vault.
- Другие облака, кроме Google Drive. Сама интеграция в объём не входит, но архитектура **обязана** позволять добавить новое облако отдельным модулем без правок движка (см. 6.4a).
- История версий и восстановление удалённого в духе Obsidian Sync (может появиться позже).
- iOS и macOS (Kotlin Multiplatform их не исключает, но сейчас в объём не входят).
- Восстановление забытого пароля. Его не будет по определению.

## 4. Анти-цели (провал, даже если «технически работает»)

- Правка тихо теряется: «побеждает тот, у кого позже mtime», без показа пользователю.
- Для установки на Windows нужны права администратора.
- Настройка требует понимания rclone/git/CLI-флагов: пользователь не обязан знать, что такое diff.
- В Drive видны имена заметок или структура папок в открытом виде.
- Конфликты на ровном месте из-за служебных файлов Obsidian (`.obsidian/workspace*.json` и т. п.).
- Пароль хранится в открытом виде в файле.

## 5. Ограничения (решено пользователем)

- Язык: **Kotlin**, Kotlin Multiplatform: один код для всех платформ.
- **Единый UI** для всех платформ на Compose (Jetpack Compose / Compose Multiplatform), а не отдельный интерфейс под каждую платформу.
- **Единый бэкенд** (движок синхронизации) для всех интерфейсов: окно на компьютере, Android, плагин Obsidian, расширение браузера и web UI работают через него, без собственной логики синхронизации.
- **mise** для инструментов (версии JDK и т. п.), локальных переменных и секретов.
- Артефакты собирает **GitHub Actions**: установщик для Windows, нативный пакет для Arch Linux, APK для Android, Docker-образ демона.
- Linux: **Arch в первую очередь**, нативная сборка без костылей.
- **Docker**: поддерживаемый вариант установки демона без интерфейса, в том числе на Windows для тех, у кого Docker уже стоит.
- Демон без интерфейса плюс **лёгкий web UI** к нему.
- Заготовки в скелете **под все части**: desktop, Android, плагин Obsidian, браузерное расширение, демон, web UI.
- Репозиторий: приватный GitHub.

## 6. Архитектура (предлагаемая; помечено, где решение моё)

### 6.1 Модули

```
mimir/
├─ core/               # KMP: jvm, android, js, wasmJs — без платформенных зависимостей
│   ├─ crypto/         #   формат шифрования (совместимый с rclone crypt), KDF из пароля
│   ├─ sync/           #   движок: состояние файлов, план синхронизации, обнаружение конфликтов
│   ├─ rules/          #   правила: Wi-Fi, расписание, исключения
│   └─ api/            #   интерфейсы: RemoteStorage, LocalVault, SecretStore, NetworkState, Clock
├─ drive/              # KMP: реализация RemoteStorage для Google Drive API (OAuth, право drive.file)
├─ ui/                 # Compose Multiplatform: ВСЕ экраны (статус, настройки, конфликт, быстрый просмотр)
│                      #   таргеты: android, jvm(desktop), wasmJs(web UI)
├─ app-desktop/        # тонкая запускалка: main(), трей, автозапуск; Windows + Linux
├─ app-android/        # тонкая запускалка: Activity, фоновая служба/WorkManager, разрешения
├─ daemon/             # headless-запуск движка (JVM): конфиг из файла/env, HTTP API для web UI и плагина
├─ web-ui/             # сборка ui под wasmJs, раздаётся демоном
├─ obsidian-plugin/    # Kotlin/JS: статус синхронизации внутри Obsidian, ходит в локальный API движка
├─ browser-extension/  # Kotlin/JS: расшифровка/просмотр заметки поверх Google Drive, crypto из core
├─ packaging/
│   ├─ arch/PKGBUILD   # сборка .pkg.tar.zst
│   ├─ windows/        # настройки MSI (per-user)
│   └─ docker/Dockerfile
├─ .github/workflows/  # CI: сборка, тесты, релизные артефакты
├─ mise.toml           # инструменты и задачи
├─ mise.local.toml.example
└─ docs/
```

`app-desktop` и `app-android` — **не отдельные интерфейсы**, а запускалки на несколько файлов. Отдельный Android-модуль нужен по требованиям системы сборки, весь интерфейс живёт в `ui`.

### 6.2 Единый бэкенд и как к нему обращаются

- Движок (`core.sync`) работает внутри процесса: в `app-desktop` (продолжает работу в трее после закрытия окна), в `app-android` (фоновая служба) или в `daemon`.
- Движок выставляет **локальный HTTP API** (статус, список неотправленных/устаревших файлов, конфликты, команды). Им пользуются плагин Obsidian, web UI, а в будущем и другие клиенты. *Моё решение*: HTTP плюс JSON как самый простой транспорт, доступный из Kotlin/JS внутри Obsidian и из браузера. Защита: токен в локальном конфиге.
- Адрес прослушивания настраивается. По умолчанию `127.0.0.1`, в Docker-образе `0.0.0.0` внутри контейнера, а порт пробрасывается на хост как `127.0.0.1:<port>`. Docker-сценарий: демон на **том же компьютере**, где открыт Obsidian; vault подключается bind mount'ом. Удалённый доступ (NAS, HTTPS, полноценная аутентификация) в объём не входит. *Моё решение*, исходя из сказанного пользователем о Docker.
- **API поднимает и Android-приложение**, потому что плагин Obsidian должен работать и на телефоне: главный сценарий конфликта («правка на телефоне не ушла») возникает именно там. Плагин не помечается `isDesktopOnly`. *Моё решение.*
- Окно desktop/Android обращается к движку напрямую в процессе, без HTTP.

### 6.2a Доступ к vault на Android (решение моё)

- `LocalVault` в `core` описывается через абстрактные идентификаторы файлов и потоки, а не через `java.io.File`/пути, чтобы его можно было реализовать и через Storage Access Framework.
- Первая реализация на Android использует `MANAGE_EXTERNAL_STORAGE` и обычные пути: APK распространяется вне Google Play, и с этим разрешением можно следить за изменениями файлов. Путь в Google Play (через SAF) остаётся открытым благодаря абстракции.

### 6.2b Идентификаторы (решение моё)

Имя «Mimir» рабочее. Все долгоживущие идентификаторы (`applicationId`, id плагина Obsidian, UpgradeCode MSI, имя пакета pacman, имя образа GHCR, Gradle group) задаются в одном месте (`gradle.properties` + генерация в манифесты), чтобы смена имени была одной правкой до первого публичного релиза.

### 6.3 Шифрование (решение моё, на основе разбора аналогов)

- Формат **совместимый с rclone crypt**: шифруются содержимое и имена. Имена файлов и папок шифруются по отдельности (режим rclone `filename_encryption = standard`, `directory_name_encryption = true`): в Drive вместо `Здоровье/Анализы мамы.md` лежит что-то вроде `p0e52nreeaj0a5ea7s64m4j72s/l42g6771hnv3an9cgc8cr2n1ng`. Пользователь отдельно просил, чтобы ИИ не мог понять контекст по названиям. Плюсы: открытый, проверенный формат, и запасной выход (vault можно расшифровать обычным rclone, даже если Mimir перестанет существовать). Тот же подход использует плагин Crypt Drive Sync.
- Ключ получается из пароля через scrypt ровно так, как в rclone crypt. Соль отдельно в Drive **не хранится**: используется схема rclone (необязательный второй пароль `password2`, иначе стандартная соль rclone). Совместимость с rclone важнее собственной соли, и scrypt остаётся медленным при любой соли. *Моё решение.*
- Оговорка: размеры файлов и время изменения в Drive остаются видны (как и у rclone crypt). Для задачи «Gemini не должен читать заметки» это приемлемо.
- Реализация должна собираться под JS/wasm, чтобы браузерное расширение и web UI расшифровывали тем же кодом.
- Пароль на устройстве хранится в системном хранилище секретов: Windows Credential Manager/DPAPI, Linux Secret Service (libsecret), Android Keystore; в `daemon` из env/файла с правами 600 или Docker secret.

### 6.4 Google Drive (решение моё)

- Право доступа **`drive.file`**: приложение видит только созданные им файлы. Это неприватное право, достаточно базовой проверки приложения в Google. Широкий доступ ко всему Drive не нужен.
- **Вход через стандартное окно Google** (требование пользователя): пользователь видит обычную страницу входа и согласия Google с запросом доступа к файлам Drive и данным аккаунта. Запрашиваются `drive.file` плюс `openid email profile` (чтобы показать в приложении, какой аккаунт подключён). На экране согласия Google это выглядит как «просматривать, изменять, создавать и удалять только те файлы Google Диска, которые вы используете в этом приложении», а не как доступ ко всему Диску. Так и задумано.
- Как открывается окно на каждой платформе (*моё решение*):
  - desktop: системный браузер со страницей Google, возврат на loopback-адрес приложения, PKCE;
  - Android: системный выбор аккаунта Google и экран согласия через Google Identity Services (Authorization API);
  - браузерное расширение: `chrome.identity.launchWebAuthFlow`;
  - демон в Docker: OAuth для устройств с ограниченным вводом (код на экране web UI или в логе плюс ссылка `google.com/device`), потому что loopback из контейнера ненадёжен; `drive.file` в этом режиме доступен.
- Client ID/secret берётся из mise-секретов при разработке и из секретов GitHub при сборке релизов. В скелете есть только экран «Войти через Google» и интерфейс `AuthProvider`, без реального OAuth.
- `drive.file` привязан к **проекту Google Cloud**, а не к отдельному OAuth-клиенту. Поэтому все клиенты Mimir (desktop, Android, расширение браузера, web UI/демон) заводятся в одном проекте Google Cloud и видят одни и те же файлы. Запасной выход через rclone работает, если в rclone указать client ID того же проекта (rclone позволяет задать свой). В README это нужно описать. *Моё решение.*

### 6.4a Расширяемость под другие облака (требование пользователя; паттерн — моё решение)

- Порты и адаптеры: `core` знает только порт `RemoteStorage` (листинг, чтение/запись потоков, удаление, метаданные/ревизии, обнаружение изменений) и порт `AuthProvider`. Шифрование — декоратор поверх любого `RemoteStorage` (`EncryptedRemoteStorage(inner, cipher)`), поэтому облако о шифровании ничего не знает.
- Каждое облако — отдельный Gradle-модуль-адаптер (`drive` — первый), который регистрирует фабрику `RemoteStorageProvider` (id, имя, нужные настройки, `create(config)`). Приложения собирают список провайдеров при старте. Новое облако = новый модуль + одна строка регистрации, без правок `core.sync` и `ui`.
- Возможности облаков различаются (например, есть ли у облака дешёвый feed изменений). Это описывается флагами возможностей провайдера, а движок выбирает стратегию, а не проверяет тип облака.
- В скелете: интерфейсы, фабрика, регистрация `drive` и тестовый `InMemoryRemoteStorage` в `core` (он же пригодится для тестов движка).

### 6.5 Профилактика конфликтов (замысел; в скелете только места под это)

- Индикатор состояния всегда на виду: трей/значок на desktop, постоянное уведомление/виджет на Android, строка состояния и плашка над заметкой в Obsidian («эта заметка изменена на другом устройстве и ещё не пришла сюда», «есть неотправленные правки»).
- Служебные файлы Obsidian (`workspace*.json` и т. п.) по умолчанию исключены или синхронизируются по особому правилу.
- Конфликт никогда не решается молча: сохраняются обе версии, пользователь выбирает на экране конфликта.

### 6.6 Сборка и поставка

| Платформа | Артефакт | Как |
|---|---|---|
| Windows | MSI, установка в профиль пользователя без админа | Compose Desktop / jpackage, JRE вшита |
| Arch Linux | `.pkg.tar.zst` (`pacman -U`), PKGBUILD пригоден для AUR | сборка в контейнере `archlinux` в GitHub Actions; JRE **системная**, ставится через `depends=('java-runtime>=N')` (решение пользователя) |
| Android | подписанный APK | ключ подписи в секретах GitHub |
| Docker | образ `daemon` (headless + web UI) | multi-stage Dockerfile, публикация в GHCR |
| Obsidian | zip с `main.js` + `manifest.json` | на тег, в релиз GitHub |
| Браузер | zip расширения | на тег, в релиз GitHub |

Оговорка, принятая к сведению: desktop-интерфейс Compose работает на JVM, поэтому в установщик для Windows вшивается урезанная Java (размер примерно 60–90 МБ). Пользователь её не ставит. Одиночный нативный бинарник с этим UI сейчас невозможен. На Arch Java системная.

### 6.6a Linux-десктоп пользователя: niri (Wayland)

- **Трей**: в niri нет встроенного трея, значки показывает панель (например, waybar) по протоколу StatusNotifierItem через D-Bus. Стандартный AWT `SystemTray` там не работает, поэтому на Linux нужен трей через StatusNotifierItem (библиотека на выбор исполнителя). На Windows обычный трей.
- **Окно**: Compose Desktop по умолчанию работает через AWT/X11, а в niri X11-приложения запускаются через `xwayland-satellite`. Для скелета достаточно, чтобы окно запускалось под niri с `xwayland-satellite`. Нативный Wayland (JetBrains Runtime с WLToolkit) — риск, который стоит проверить позже, потому что он может противоречить системной Java на Arch. В README указать требование.
- Браузерное расширение: **только Chromium** (Chrome, Edge, Brave и др.), Manifest V3 (решение пользователя).

### 6.7 mise

- Версии (требование пользователя: самые свежие на октябрь 2026): **Kotlin 2.4.21** (последний стабильный, 08.10.2026; 2.5.0 пока в бете), **JDK 27** (вышел 15.09.2026). Gradle не ниже 9.8, первой версии с официальной поддержкой Java 27. Исполнитель обязан проверить, что Kotlin, AGP и Compose Multiplatform поддерживают JDK 27 и как JVM для сборки, и как `jvmTarget`. Если какой-то компонент не поддерживает, откатиться на JDK 25 (LTS) только там, где это необходимо, и записать причину в README.
- Система сборки: **Gradle** (Kotlin DSL, version catalog, configuration cache и build cache включены). Альтернативы рассмотрены: Kotlin Toolchain (бывший Amper) пока в альфе, поддержка Android и упаковки не подтверждена; Maven и Bazel для KMP с Android/JS/wasm непригодны.
- `mise.toml`: версия JDK, при необходимости Node; задачи-обёртки над Gradle: `build`, `test`, `desktop`, `android`, `daemon`, `web`, `plugin`, `extension`, `package:*`.
- `mise.local.toml` (в `.gitignore`): секреты (`GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET` и т. п.). В репозитории лежит `mise.local.toml.example`.
- Gradle через wrapper (`gradlew`), mise его не заменяет.

## 7. Объём скелета (критерий готовности)

1. Все модули из 6.1 созданы и собираются одной командой (`mise run build`).
2. Каждая точка входа запускается и показывает заглушку: окно desktop с экраном-заглушкой из `ui`, Android-приложение с тем же экраном, демон отвечает на `GET /health`, web UI открывается в браузере из демона, плагин Obsidian загружается и пишет в строку состояния «Mimir: not connected», расширение браузера устанавливается и показывает popup-заглушку.
3. В `core` определены интерфейсы из 6.1 (`RemoteStorage`, `RemoteStorageProvider`, `AuthProvider`, `LocalVault`, `SecretStore`, `NetworkState`, `SyncEngine`, `ConflictResolver`, `Cipher`) с пустыми/заглушечными реализациями и хотя бы одним проходящим unit-тестом.
4. GitHub Actions: на push сборка и тесты; на тег сборка MSI, `.pkg.tar.zst`, APK, Docker-образа (подпись/публикация могут быть заглушками до появления секретов, но шаги присутствуют).
5. `mise.toml`, `mise.local.toml.example`, `.gitignore`, `README.md` с инструкцией «как начать разработку», `docs/` с этим документом.
6. Реальной синхронизации, шифрования и OAuth в скелете **нет**.

## 8. На усмотрение исполнителя

- Конкретные версии Kotlin, Compose Multiplatform, AGP, Gradle (актуальные стабильные на момент сборки).
- Библиотеки: HTTP (Ktor ожидаем, но не обязателен), сериализация, криптопримитивы (с условием, что они собираются под JS/wasm), DI (или без него).
- Структура пакетов внутри модулей, имя Gradle-группы (`io.github.<user>.mimir` или аналог).
- Как именно демон раздаёт web UI и как устроен локальный токен.
- Способ сборки браузерного расширения (Manifest V3) и плагина Obsidian (Kotlin/JS → `main.js` + `manifest.json`).
- Структура workflows GitHub Actions (один или несколько файлов, матрица).

## 9. Справочно: аналоги

- [Crypt Drive Sync](https://community.obsidian.md/plugins/crypt-drive-sync): плагин Obsidian, Android, формат rclone crypt, при конфликте хранит обе версии. Хорошая идея формата.
- [Encrypted GDrive Sync](https://community.obsidian.md/plugins/encrypted-gdrive-sync): шифрует только содержимое, имена и структура видны. Для нас неприемлемо.
- [Remotely Save](https://community.obsidian.md/plugins/remotely-save): Google Drive только в платной версии, конфликты по «последнему mtime». Анти-пример. [Форк](https://gitea.astro-vps.duckdns.org/bruno/remotely-save/src/tag/0.5.19) с настраиваемыми стратегиями конфликтов.
- [Google Drive API scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth): основание для выбора `drive.file`.

Все эти решения живут внутри Obsidian. Отдельного приложения уровня Drive Desktop без прав администратора не найдено.
